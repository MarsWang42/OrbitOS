# 知识沉淀要经过验证复盘闭环

## 核心原则

学到的内容不能因为“看起来对”就直接当成稳定知识，而应经过实际使用、审查和复盘，才能沉淀成正式知识。

## 推荐闭环

`执行 -> 自审 -> 他审 / 审核 -> 项目验证 -> 复盘 -> 知识沉淀`

补一句更完整的理解：

`复盘` 不只是判断这次成没成功，也应用来反向更新知识结构和思维方式。

## 成功不只看一个结果

判断是否“成功”，至少要看这几类维度：

- 结果质量：产出是否真的解决问题
- 成功率：放进项目后，是否稳定提高成功概率
- 效率与成本：是否节省时间、降低返工、减少试错成本
- 稳定与复用：是否能在相似任务里重复成立
- 协作与可追溯：是否能清楚回看是谁做的、怎么审的、为什么成立

同时要区分：

- 哪些是内部执行与流程带来的结果
- 哪些是外部环境、平台或宏观变量带来的影响

## 角色分工

- `谋士`：负责组织闭环，决定是否进入正式沉淀
- 专家角色：先做自审，再提交结果
- `审核` 或其他角色：承担他审与放行
- `Obsidian`：负责保存自审细节、验证结果、复盘结论和最终知识

## 记录建议

- 自审细节：优先留在项目页、研究页或 `OpenClaw配置/03_知识摘录`
- 他审意见：留在审核记录或项目/研究的复盘区块
- 项目验证结果：留在 `20_项目` 与 `10_日记`
- 稳定结论：最后提炼进 `40_知识库`
- 如果某套判断长期失效：回写并更新原有知识卡、SOP 或思维模式说明
