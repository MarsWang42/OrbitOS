# 官方来源纳入日常学习流

## 一句话结论

`OpenClaw GitHub Releases API` 和 `Obsidian Changelog RSS` 最适合进入“轻量高频巡检”学习流，而不是走“链接学习 -> 长篇深挖”的重流程。

## 适用场景

这条流程只处理两类输入：

- `OpenClaw` 官方版本发布
- `Obsidian` 官方更新日志

它们的共同特点是：

- 来源官方
- 结构化程度高
- 更新频率可控
- 更适合先做“变化判断”，再决定是否深挖

## 默认动作

### 第 1 步：先看是否有“新变化”

- `OpenClaw`
  - 看最新 release 标题、版本号、发布时间、正文摘要
- `Obsidian`
  - 看 changelog 标题、发布日期、更新点摘要

目标不是一次性全读完，而是先判断：

- 这次有没有和当前系统直接相关的变化
- 是“值得行动”，还是“只需知道”

### 第 2 步：按影响级别分流

#### A. 只需知道

如果更新满足以下情况：

- 只是常规修复
- 和当前 `OpenClaw + Obsidian` 主方向弱相关
- 暂时不会影响已有链路

那就只做两件事：

- 在今日日记留一条极简记录
- 不单独升级为研究 / 知识 / 项目动作

#### B. 值得研究

如果更新满足以下情况：

- 可能改变工作流
- 可能补当前卡点
- 可能影响工具链、自动化或平台接入

那就：

- 新建或补充 `30_研究`
- 记录“变了什么、为什么值得看、下一步要不要验证”

#### C. 需要行动

如果更新满足以下情况：

- 会直接影响当前项目推进
- 需要补配置、补 SOP、补接入方式
- 需要安排验证

那就：

- 回写 `20_项目`
- 增加 1 到 3 条下一步动作
- 同步今日日记

#### D. 已经足够稳定

如果某条结论已经经过多次验证，且具有长期复用价值，才考虑：

- 提炼到 `40_知识库`

不要把一次版本更新直接写成稳定知识。

## 当前推荐的节奏

### OpenClaw

- 频率：低频巡检
- 默认看点：
  - 新版本
  - 新能力
  - 配置变化
  - 破坏性变更

### Obsidian

- 频率：低频巡检
- 默认看点：
  - CLI
  - 插件能力
  - 自动化相关接口
  - 会不会影响 Vault 工作流

## 最小落盘规则

### 只记日记

适用于：

- 更新存在
- 但对当前系统影响不大

### 记研究

适用于：

- 更新可能改变当前判断
- 但还没有进入执行阶段

### 记项目

适用于：

- 更新已经触发了明确动作
- 需要安排验证、配置或流程调整

### 记知识

适用于：

- 已经跨多轮验证
- 可以上升为长期稳定原则

## 这条流程解决什么

- 避免把所有官方更新都做成重研究
- 避免明明该进项目的变化，只停在“看到了”
- 避免把一次更新直接误提炼成长期知识

## 推荐默认顺序

`官方源巡检 -> 判断影响级别 -> 日记 / 研究 / 项目分流 -> 验证后再决定是否提炼知识`

## 当前下一步

可以直接拿 2 个真实样本验证这条流程：

1. 取 1 条 `OpenClaw` release 更新
2. 取 1 条 `Obsidian` changelog 更新
3. 分别判断它们应落到：
   - 只记日记
   - 研究
   - 项目
