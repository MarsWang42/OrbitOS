# 官方来源真实样本分流验证

## 一句话结论

这次用 `1` 条 OpenClaw 官方 release 和 `1` 条 Obsidian 官方 changelog 做验证后，可以先把默认分流收成两条：

- `OpenClaw` 官方 release：更适合优先落到 `20_项目`
- `Obsidian` 官方 changelog：更适合优先落到 `30_研究`

## 样本 A：OpenClaw 官方 release

### 来源

- 来源类型：GitHub Releases
- 日期：`2026-03-14`
- 版本：`openclaw 2026.3.13`
- 链接：https://github.com/openclaw/openclaw/releases

### 这次更新里和当前系统最相关的点

- `Docker: add OPENCLAW_TZ timezone support`
- `fix(feishu): add early event-level dedup to prevent duplicate replies`
- `macOS: respect exec-approvals.json settings in gateway prompter`

### 为什么不只记日记

这次不是普通修修补补，因为它直接碰到了你当前项目最关心的几条线：

- 飞书前台稳定性
- 时区与定时行为
- macOS 上的执行审批体验

这些都不是“知道一下就行”，而是和当前 `OpenClaw` 生产级验证直接相关。

### 为什么先落项目，不先落知识

这类 release 的第一反应应该是：

- 先判断会不会影响当前链路
- 再安排验证动作

它还没有经过你本地验证，所以现在不适合直接提炼成稳定知识。

### 当前分流判断

`20_项目`

### 推荐下一步动作

1. 验证 Feishu 去重修复是否能减少重复回复
2. 验证 `OPENCLAW_TZ` 是否能改善时区一致性
3. 看 macOS 审批行为是否和当前工作流更一致

## 样本 B：Obsidian 官方 changelog

### 来源

- 来源类型：官方 changelog
- 日期：`2026-02-27`
- 版本：`Obsidian 1.12 Desktop`
- 链接：https://obsidian.md/changelog

### 这次更新里和当前系统最相关的点

- 官方正式引入 `Obsidian CLI`
- 明确支持从终端控制 Obsidian，用于脚本、自动化和外部工具集成
- `daily:prepend` 等命令行为也给出了更清晰的自动化语义

### 为什么不直接进项目

它当然和项目高度相关，但这类变更更像“能力入口变化”，还需要先回答：

- CLI 能替代你现在哪些手工动作
- CLI 更适合接在哪一段链路
- 会不会影响现有 Vault 工作流

这一步更像“先研究，再决定项目动作”。

### 为什么不是只记日记

因为这不是普通版本说明，而是明显改变了后续自动化可能性的入口变化。  
对当前方向，它足以单独触发一轮研究判断。

### 当前分流判断

`30_研究`

### 推荐下一步动作

1. 单独研究 CLI 能覆盖哪些 Obsidian 操作
2. 判断它是否适合接入 `日记 / 研究 / 项目` 写入链路
3. 再决定是否回写项目动作

## 这次验证后形成的默认判断

### 1. OpenClaw 官方更新

如果 release 内容直接涉及：

- 飞书 / Discord / Slack / Telegram 等前台通道
- Docker / 时区 / gateway / 配置行为
- 你当前正在验证的运行链路

优先落到：

- `20_项目`

### 2. Obsidian 官方更新

如果 changelog 内容直接涉及：

- CLI
- 自动化入口
- 插件能力
- Vault 工作流变化

优先落到：

- `30_研究`

先研究，再决定要不要升成项目动作。

## 当前结论

“官方来源默认学习流”已经不只是原则，经过这次真实样本验证后，可以先按下面执行：

- `OpenClaw 官方 release`：默认优先看成项目输入
- `Obsidian 官方 changelog`：默认优先看成研究输入
